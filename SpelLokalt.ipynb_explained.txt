====================================================================
EXPLANATION: SpelLokalt.ipynb
====================================================================

What this file is: "SpelLokalt" is Swedish for "Game Locally" — this
is the actual playable game. It's a Jupyter notebook rather than an
ordinary ".py" file, which means it's made up of separate "cells" that
get run one at a time, in order, from top to bottom, inside a tool
like Jupyter Notebook or JupyterLab, rather than being run all at once
from the command line. Because later cells rely on things defined in
earlier cells (variables, functions, classes), running them out of
order — or skipping one — will cause errors or broken behavior. Every
time you want to (re)start the game, you're expected to re-run the
cells from the top.

This notebook uses "pygame" (a popular Python library for building
simple 2D games) to open a window, draw images to the screen, and read
keyboard input. It also connects to the separate multiplayer server
(server.py) using the NetClient class from netcode.py, so that this
player's game window can show other players moving around live.

A few game-development terms used throughout this explanation:
 - "sprite" / "image": a picture used to represent something on
   screen — the frog, a bush, a tile of ground, etc.
 - "tile": one small, reusable square image (like one ground block)
   that gets repeated many times to build up a bigger scene, the way
   you'd tile a floor with identical tiles.
 - "rect" (rectangle): a simple box shape defined by an x/y position
   plus a width and height, used constantly in this file to represent
   "where something is and how big it is," and to check whether two
   things are overlapping (a "collision").
 - "x / y coordinates": positions in the game world. x increases to
   the right; y INCREASES DOWNWARD (this is the opposite of ordinary
   graph paper, but standard for computer screens/games) — so a
   *smaller* (more negative) y value means *higher up* in this game,
   which matters a lot for understanding the world-layout data below,
   since the world is built going upward.
 - "frame": one single drawn image, shown for a fraction of a second;
   a game is really just many frames shown one after another, fast
   enough to look like smooth motion.

--------------------------------------------------------------------
CELL 0 — Imports and setup
--------------------------------------------------------------------
What it's for: Loads all the outside tools this notebook depends on,
and starts up pygame itself.

How it works: The very first lines are commented-out shell commands
(starting with "#!"), left in the cell as a reminder of the one-time
setup steps ("create a virtual environment", "activate it", "install
pygame-ce and ipykernel") rather than code that runs — they're notes
to a human, not instructions to Python.

It then imports a handful of Python's own built-in tools (of which
"pickle" and "threading" aren't actually used directly anywhere else
in this notebook — likely leftovers from earlier experimentation, the
same way netcode.py has an unused "import math"; "os", "socket", and
"struct" are similarly unused here directly, since NetClient in
netcode.py handles all of that internally — while "shelve" IS used
later, for the login/account system in cell 18), the pygame library
itself, Python's "random" number generator (used later for scattering
decorations around the world), and this project's own NetClient class
from netcode.py (the piece that handles talking to the multiplayer
server). Finally, "pygame.init()" performs pygame's required startup
steps, which must happen before any other pygame feature (like opening
a window or loading an image) is used.

--------------------------------------------------------------------
CELL 1 — Loading images
--------------------------------------------------------------------
What it's for: Opens the game window and loads every image the game
will need onto it in advance, so the main game loop later on can just
draw them quickly without pausing to load anything from disk.

How it works: First, the size of the player's actual display is
detected with "pygame.display.Info()" and a window is created at
exactly that size ("screen_width" x "screen_height") — this is a
change from always opening a fixed 1920x1080 window; now the game
window fills whatever screen it's run on, whatever size that is.
Then, one by one, image files are loaded from disk: two different sky
backgrounds (red and blue — used for different "heights" in the game,
see the Camera class below), a "victory" image shown when the player
wins a level (scaled to a quarter of the screen's area and given
partial transparency via "set_alpha(245)", so it visibly overlays
rather than fully replacing what's underneath), a "Game Over" image
shown on death (loaded with "convert_alpha()" instead of "convert()"
because, unlike the fully-opaque backgrounds and win image, this one
is a PNG with its own transparent areas that need to be preserved),
and two "tilesheets" (single image files containing several smaller
pictures packed together side by side): "terrainSheet.png" and
"world_tileset.png". For each of these full-image files, some
processing happens: "convert()"/"convert_alpha()" reformats the image
into a form pygame can draw much faster (this is a standard,
recommended step after loading any image in pygame — "convert_alpha()"
specifically is used whenever the image needs to keep transparent
pixels, "convert()" when it's fully opaque), and
"pygame.transform.scale"/"scale_by" resizes them (the backgrounds are
stretched to exactly fill the screen; other images are enlarged 3x
their original pixel size, since the source art is small and pixelated
by design).

From the two tilesheets, several smaller pieces are cut out using
".subsurface(pygame.Rect(...))" — this carves out one small rectangle
from a bigger sheet, treating that rectangle as its own separate image:
the platform tile, a "ground" tile (the top surface of the terrain), a
"below" tile (the terrain underneath the surface), a pumpkin
decoration, a green bush decoration, an exclamation mark (used to mark
a special checkpoint in the world — see the CheckPoint class below),
and an orange bush decoration. Each of these cut-out pieces is then
also enlarged 3x, matching the rest of the art. (Note: unlike an
earlier version of this notebook, the player's frog image is no longer
cut out here individually — see cell 2's pick_character, which cuts
character images out on demand from a whole sheet of options instead
of there being just one fixed frog image.)

Finally, this cell also loads "CharSprites.png" (a sheet of 16
different playable character images, used by pick_character in cell 2)
and "YellowBird-Idle.png" (used for the Enemy class, further down),
cutting one 32x32 pose out of the bird sheet and enlarging it 2.5x.

--------------------------------------------------------------------
CELL 2 — char_list and pick_character(choice)
--------------------------------------------------------------------
What it's for: Lets the player pick which of 16 pre-drawn character
images they want to look like, instead of everyone always playing as
the same frog. "choice" is a number from 1 to 16 (see cell 18, where
the player is asked to type this number in), and this function turns
that number into the actual cut-out image to draw.

How it works: "char_list" is built once, up front, as a list of 16
(column, row) positions — a 4x4 grid — using a nested comprehension
("for rad in range(4) for kolumn in range(4)"; "rad"/"kolumn" are
Swedish for "row"/"column"). This describes where, within the
CharSprites.png sheet (loaded in cell 1), each of the 16 character
images sits, assuming each one is a 64x64 pixel square tile in that
grid.

"pick_character(choice)" then looks up the (column, row) position for
the given choice (subtracting 1, since the player types choices
starting at 1 but list positions start at 0), cuts that one 64x64
square out of the sheet with ".subsurface(pygame.Rect(...))", enlarges
it 1.5x, and returns it — ready to be used as either this player's own
sprite (see the Player class) or drawn for a remote player (see
Camera.render_world, and RemotePlayerState in
netcode.py_explained.txt).

Why it's built this way: This is called both for the local player
(once, in cell 21) and repeatedly for every other, remote player every
single frame (in Camera.render_world) — since remote players are only
described by a plain "char" number sent over the network (see
RemotePlayerState in netcode.py_explained.txt), this function is what
turns that number back into an actual picture to draw. Unlike the
notebook's own tinted_frog-style caching elsewhere in earlier versions
of this project, this function re-cuts the image from the sheet every
single time it's called rather than caching results — for a 16-entry
sheet and this game's scale, that's cheap enough not to matter, but it
does mean it's doing more work per frame than strictly necessary if
many remote players are visible at once.

--------------------------------------------------------------------
CELLS 3-5 — Basic world-layout data (PLATFORMS, GROUND, BELOW)
--------------------------------------------------------------------
What this data is: These cells don't define any functions — they
build plain lists of x/y positions that describe where things sit in
the game world. This hand-designed layout is effectively "the level"
— there's no separate level file or level editor; the world is defined
directly as data, right here in the notebook.

PLATFORMS (cell 3): First, the actual pixel width/height of one
platform tile is read off the image loaded earlier. Then PLATFORMS is
a hand-written list of 16 (x, y) positions — each one the top-left
corner of one free-floating platform placed somewhere in the world.
Remember, more negative y means higher up, so this list places
platforms at a wide range of heights, mostly going up (the numbers get
increasingly negative).

GROUND (cell 4): This builds a long, evenly-spaced row of ground tile
positions, laid side-by-side, forming a continuous strip of solid
ground near the bottom of the starting area of the world (from x=-100
up to x=3000, one tile-width apart). This is the "floor" the player
starts standing on.

BELOW (cell 5): Similar idea, but building a filled-in block *beneath*
that strip of ground (10 rows deep), so the ground looks solid from
above rather than being a paper-thin floating strip with empty space
visible underneath it.

--------------------------------------------------------------------
CELL 6 — make_island(x, y, width, height)
--------------------------------------------------------------------
What it's for: A reusable helper function for generating one "island"
— a small floating platform made of ground tiles on top and filled-in
tiles underneath, similar in spirit to the ground built in cells 4-5,
but sized and placed wherever you like instead of being one long
continuous strip.

How it works: "x" and "y" describe where the island's top-left ground
tile should be; "width" and "height" describe how many tiles wide and
how many tiles tall the island should be (measured in tile-units, not
pixels). Two safety checks ("assert") run first, refusing to continue
if width or height fall outside sensible ranges (2 to 18 tiles wide,
2 to 10 tiles tall) — this is a guard against accidentally passing in
a nonsensical size by mistake, since these numbers come from
hand-typed data in the next cell. The function then builds two
separate lists: one row of "ground_tiles" positions (the visible top
surface, spanning the given width), and a block of "below_tiles"
positions beneath it (filling in all the remaining rows down to the
given height, across the same width), then returns both lists as a
pair.

--------------------------------------------------------------------
CELL 7 — ISLANDS (data) and building the rest of the world
--------------------------------------------------------------------
What this data is: ISLANDS is a large, hand-written list of islands to
place in the world — 47 entries, each one an (x, y, width, height)
tuple describing one island's position and size, using the
make_island helper from the previous cell. Reading down the list, the
y values generally become more and more negative, meaning the islands
are laid out as a winding path leading upward, further and further
from the starting ground.

After the list itself, a loop runs through every entry in ISLANDS,
calls make_island for each one to actually generate its tile
positions, and appends the results onto the same GROUND and BELOW
lists that were started back in cells 4-5 — so by the end of this
cell, GROUND and BELOW together describe the starting ground strip
AND every island, combined into two single, complete lists that the
rendering code (see Camera, below) doesn't need to treat any
differently from each other.

--------------------------------------------------------------------
CELLS 8-10 — Decorations: make_pumpkins, make_bushes (x2)
--------------------------------------------------------------------
What these are for: These three cells scatter decorative objects
(pumpkins, green bushes, and orange bushes) across the islands built
above, purely for visual variety — none of these objects affect
collision or gameplay.

How they work: All three functions follow the same pattern, just with
different starting positions and different spacing. Each one creates
its own random number generator seeded with a fixed number (1334) —
using a fixed "seed" like this means the random-looking placement is
actually the same every single time the program runs, so decorations
don't jump around between sessions even though "random" numbers are
being used to place them. Each function starts by placing one decor-
ation item on the ground near the very start of the world (at a
specific hardcoded x position), then walks forward through the
ISLANDS list, skipping a small random number of islands each time (a
different random range for each decoration type, so pumpkins, green
bushes, and orange bushes don't all appear on exactly the same
islands), and places one item at a random tile position along the top
of whichever island it lands on. This repeats until it's stepped past
the end of the islands list, at which point the finished list of
positions is returned.

Note: the function in cell 10 is also named "make_bushes" — a second
function with the exact same name as the one defined in cell 9. In
Python, defining a function with a name that already exists simply
replaces the old one, so after cell 10 runs, the name "make_bushes"
only refers to the orange-bush version; this doesn't cause an error,
but it does mean the two functions can't both be referred to by that
name later (which isn't a problem here, since neither is called again
after producing its one result list).

The three resulting lists — PUMPKINS, BUSHES, and ORANGE_BUSHES — are
each just a list of (x, y) positions, in the same style as GROUND and
PLATFORMS, ready to be drawn by the Camera class.

Note on player appearance: an earlier version of this notebook had a
"tinted_frog" function here that recolored one fixed frog image using
whatever color the server assigned a player (see the "note on player
'char'" in server.py_explained.txt for how that system worked). That
function is gone — it's been replaced by cell 2's pick_character,
which instead picks one of 16 distinct pre-drawn character images
based on a number the player explicitly chooses (see cell 18, below),
rather than recoloring a single shared image.

--------------------------------------------------------------------
CLASS: Camera
--------------------------------------------------------------------
What it's for: The Camera is responsible for everything about
*drawing* the current frame — deciding what part of the world is
visible (since the world is much bigger than the screen, and the
screen needs to scroll to follow the player), picking the right
background image, drawing every layer of the scene (background,
checkpoint marker, platforms, ground, decorations, enemies, other
players, and finally this player) in the correct order, back-to-front,
and showing the death and win overlays when either happens.

Camera.__init__(self)
    Sets up the camera's starting state: it isn't offset from the
world at all yet (offset_x and offset_y both start at 0 — these
represent how far the drawn scene needs to be shifted so the player
appears centered on screen), a leftover "move_speed" value that
doesn't currently appear to be used anywhere else in the code, and a
starting background image (the red sky).

Camera.follow(self, player)
    Adjusts the camera's vertical offset so that the given player
character stays centered on screen vertically, no matter how high up
in the world they've climbed. It works by taking half the screen's
height and subtracting the player's current y position — as the
player's y becomes more negative (climbing higher), the offset grows,
which is what makes the whole scene appear to scroll downward as the
player climbs upward, keeping the player visually centered instead of
drifting off the top of the screen. (Horizontal following is written
directly below this as a comment but is disabled — the world doesn't
scroll left/right, only vertically.)

Camera.death_screen(self)
    Draws the "Game Over" image (loaded in cell 1) centered on screen
(at a quarter of the screen's width and height in from the top-left
corner, which centers an image that's itself a quarter of the screen's
size). It doesn't clear the screen or wait for anything itself — it
just draws the overlay; the main loop (cell 21) is what actually flips
this to the display and pauses afterwards, once per death.

Camera.win_screen(self, player)
    Draws the "you win" image centered on screen the same way
death_screen does, then directly resets the given player's position
back to (500, 500) — sending them back to the start of the world — and
then, unusually for a method on Camera, itself calls
"pygame.display.flip()" (to actually show the win image, since the
main loop's own flip happens later in the frame, after this) and
"pygame.time.wait(3000)" to pause the whole game for 3 real seconds so
the player has time to see it before play resumes.

Camera.render_world(self, platforms, ground, below, pumpkins,
bushes, orange_bushes, player, enemies, checkPoint, remotes=())
    This is called once per frame and does the actual drawing of
    everything on screen, in this order (later items are drawn on top
    of earlier ones). Note this method now takes the player, the list
    of enemies, and the checkpoint directly as arguments (rather than
    only taking world-decoration lists and remotes, as an earlier
    version did), since it now needs all three to draw and check
    against them.
     1. Calls "follow" (above) to update the camera's offset based on
        where the player currently is.
     2. Clears the screen to solid black, so no leftover pixels from
        the previous frame linger underneath the new drawing.
     3. Computes a "visible window" in world coordinates —
        min_render_x/max_render_x/min_render_y/max_render_y — a
        rectangle roughly the size of the screen (plus a 100-pixel
        margin on every side) centered around the player. Every item
        drawn further down is checked against this window before being
        drawn, and skipped if it falls outside it. This is a form of
        "view culling": with the world containing many hundreds of
        tiles and decorations spread out over a huge vertical distance,
        it would be wasteful to ask pygame to draw every single one of
        them every single frame when only a small fraction are ever
        actually visible on screen at once.
     4. Decides which background image to use based purely on the
        player's height: at or below -5000 (i.e. high up) it's the
        blue sky; above that (closer to the ground, since less
        negative y means lower down) it's the red sky — giving the
        player a sense of having climbed into a different "zone" the
        higher they get.
     5. Draws whichever background image was chosen, filling the
        whole screen.
     6. Draws the checkpoint's marker image (the exclamation mark) at
        its own x/y position, shifted by the camera offset like
        everything else — see the CheckPoint class, below, for where
        that position comes from.
     7. Draws every platform, then every ground tile, then every
        "below" tile, then every pumpkin, then every green bush, then
        every orange bush — each one by looping over its list of (x, y)
        positions, skipping any that fall outside the visible window
        computed in step 3, and drawing the rest at their position
        shifted by the camera's current offset.
     8. Draws every enemy (see the Enemy class, below) the same way,
        culled against the visible window using the enemy's own
        current position.
     9. Draws every "remote" player (every other player currently
        connected, as reported by the server) using pick_character
        (cell 2) to fetch the correct sprite for that player's chosen
        character number. Remote players are NOT culled against the
        visible window — every remote player currently known is drawn
        every frame regardless of position.
     10. Finally, draws this player's own image on top of everything
         else, at their own current position (also shifted by the
         camera offset).
     11. Checks "checkPoint.win(player)" (see CheckPoint, below); if it
         returns true (the player is touching the checkpoint), calls
         "self.win_screen(player)" to show the win overlay and reset
         the player back to the start.

    Why it's built this way: Everything is drawn in a fixed
    back-to-front order (background, then world, then enemies, then
    other players, then yourself last) because in 2D drawing, whatever
    is drawn most recently appears "in front" — there's no separate
    depth/layering system, so draw order alone determines what's
    visually on top of what. The view-culling window (step 3) exists
    purely as a performance optimization, now that the world (and the
    number of decorations in it) has grown large enough that drawing
    absolutely everything every frame would start to cost noticeably
    more than it needs to.

--------------------------------------------------------------------
CLASS: Player
--------------------------------------------------------------------
What it's for: Represents this player's own character — their
position, how they move, how gravity affects them, and now also
whether they're currently dead (having fallen too far, or been hit by
an enemy — see the Enemy class, below). (Other, *remote* players are
represented much more simply, just as plain data in a
RemotePlayerState from netcode.py — they don't get their own Player
object, since their movement is entirely dictated by the server, not
by local physics.)

Player.__init__(self, image, camera)
    Sets up a new player at a fixed starting position (x=300, y=300),
    with a starting horizontal speed of 10 (pixels per frame),
    vertical velocity of 0 (not currently falling or rising), a
    gravity strength of 0.75 (how much faster the player falls each
    frame), a jump power of -20 (an initial upward velocity applied
    when jumping — negative because upward is negative y), and a flag
    tracking whether the player is currently standing on solid ground
    (starts as False). It also stores the image to draw for this
    player (now whichever character image pick_character produced for
    their chosen character number — see cell 21) and a reference to
    the Camera (though the camera reference doesn't currently appear to
    be used elsewhere on the Player itself). It creates a "rect" — a
    rectangle matching the player's current position and the size of
    their image — which is kept up to date and used for collision
    checks (see handle_platform_collision, below). Finally, three more
    pieces of state are set up: "dead" (starts False — whether the
    player currently needs to respawn), and "flipped"/"timeToFlip",
    a small pair of flags used purely to control which way the
    player's sprite is currently facing (see move, below).

Player.get_rect(self)
    A small helper that builds and returns a fresh rectangle matching
    the player's *current* x/y position and image size. This is called
    whenever up-to-date collision information is needed, since the
    player's stored "rect" attribute can otherwise go stale as soon as
    x or y changes.

Player.move(self, left, right, jump)
    Updates the player's position based on which movement keys are
    currently being held down (as determined by handle_input, further
    down). "left" and "right" are True/False flags for whether those
    keys are pressed (these are two separate "if" checks, not
    "if/elif", so if both happen to be held at once, both run — the x
    adjustments then mostly cancel out, but the sprite-flip bookkeeping
    below still runs for both).

    If left is pressed: the player's x decreases (moves left) by their
    speed; then, only if "timeToFlip" happens to currently be True, the
    image is flipped horizontally (via
    "pygame.transform.flip(self.image, self.flipped, False)", using
    whatever "self.flipped" currently is) and "timeToFlip" is cleared
    back to False.

    If right is pressed: the player's x increases by their speed; the
    image is unconditionally flipped the same way; then, only if
    "timeToFlip" is currently False, it's set to True; and finally
    "self.flipped" is unconditionally set back to False.

    Between them, these two blocks are what makes the sprite visually
    turn to face whichever direction the player is currently walking,
    using "timeToFlip"/"flipped" as leftover state from one frame to
    the next to track "has this direction already been flipped for?" —
    the exact frame a flip happens on depends on which keys were
    pressed in which order, which makes the precise timing a little
    hard to predict just from reading the code, but the overall effect
    (character faces the way it's moving) is what matters. If the jump
    key is pressed AND the player is currently
    standing on the ground, the player's vertical velocity is set to
    the (negative) jump_power, giving them an instant upward boost, and
    "on_ground" is set to False, since they've now left the ground. A
    comment notes that "self.speed" is reassigned to 10 every single
    call as a workaround for an unresolved bug the developers ran into,
    related to how pygame handles this value — meaning this isn't dead
    code that can just be deleted, even though it looks redundant with
    the value already set in __init__.

Player.apply_gravity(self)
    Simulates the effect of gravity on the player, called once per
    frame regardless of input. The player's vertical velocity
    increases by the "gravity" amount each frame (making them fall
    faster and faster over time, as real gravity would), but that
    velocity is capped at a maximum of 30 (a "terminal velocity" of
    sorts, preventing the player from ever falling arbitrarily fast —
    this cap was previously 20; it's since been raised to 30). The
    player's y position is then updated by that velocity — this is
    what actually moves the player downward when falling, or slows
    down and reverses their rise after a jump, since jumping sets a
    negative velocity that gravity then continuously counteracts.
    Finally, if the player's y position has fallen past 3000 (meaning
    they've fallen all the way off the bottom of the world, having
    missed every platform on the way down), their vertical velocity is
    reset to 0 and "dead" is set to True — this is what triggers the
    death screen and respawn in the main loop (cell 21), and is a new
    behavior; falling off the world previously had no special handling.

--------------------------------------------------------------------
CELL 13 — handle_input()
--------------------------------------------------------------------
What it's for: Reads the current state of the keyboard and translates
it into the simple left/right/jump flags that Player.move (above)
expects.

How it works: It asks pygame for the current pressed/not-pressed state
of every key, then picks out specifically whether the "A" key, the "D"
key, and the Space bar are currently held down, returning those three
True/False values together. ("A"/"D" are commonly used in games as
left/right movement keys, alongside or instead of arrow keys.)

--------------------------------------------------------------------
CELL 14 — SOLID_RECTS (data)
--------------------------------------------------------------------
What this data is: A single combined list of rectangles representing
every solid thing in the world the player can stand on or bump into:
one rectangle for every platform, every ground tile, and every "below"
tile, all built from the position lists established earlier and each
one's known tile size. This combined list is what
handle_platform_collision (next) actually checks the player against —
decorative items like pumpkins and bushes are deliberately left out,
since they're purely visual and the player should be able to walk
through them.

--------------------------------------------------------------------
CELL 15 — handle_platform_collision(player, platform_rects)
--------------------------------------------------------------------
What it's for: This is the function that stops the player from
falling through the ground or platforms, and lets them stand on top of
things — implementing solid collision.

How it works: It starts by refreshing the player's rectangle to match
their current position (since it may have moved since the last
collision check) and assumes, until proven otherwise, that the player
is not currently standing on anything ("on_ground" is reset to False).

It then checks the player's rectangle against every single solid
rectangle in the given list, one at a time. For each one that doesn't
currently overlap the player at all, it's skipped immediately — there's
nothing to resolve.

For every rectangle that DOES overlap the player, the function figures
out, in each of the four directions, exactly how much the two shapes
are overlapping — imagine pushing the player out of the obstacle in
each of the four possible directions (up, down, left, right) and
measuring how far each push would need to be to fully separate them.
The function then decides which direction actually makes the most
sense to resolve the overlap in, using both the amount of overlap and
the player's current vertical motion as clues:

 - If the player is currently moving downward (falling) AND the
   smallest overlap is the "top" one (meaning the player's feet have
   just sunk into the top of this obstacle), the player is pushed back
   up out of the obstacle by exactly that overlap amount, their
   vertical velocity is stopped (set to 0, so they don't keep trying to
   fall through), and they're marked as now standing on solid ground.
   This is the ordinary "landing on top of something" case.

 - Otherwise, if the player is currently moving upward (jumping) AND
   the smallest overlap is the "bottom" one (meaning the player's head
   has bumped into the underside of this obstacle), the player is
   pushed back down by that overlap amount and their upward velocity
   is stopped — this is "hitting your head on a platform while
   jumping."

 - Otherwise, the overlap must be primarily horizontal, so the player
   is pushed back out sideways instead — to the left if the leftward
   overlap is smaller, or to the right otherwise — which is what stops
   the player from walking straight through the side of a platform or
   wall of ground/below tiles.

After resolving one overlap, the player's rectangle is recalculated
(since their position may have just changed) before continuing on to
check the remaining solid rectangles in the list — this matters
because a player can realistically be touching more than one solid
tile at once (for example, standing exactly on the border between two
ground tiles), and each one needs to be checked against the player's
up-to-date position.

Once every solid rectangle has been checked, the function returns
whether the player ended up on solid ground, which — although the
Player object itself already tracks this as "on_ground" — is also
handed back directly to whatever called this function, in case it's
useful there too.

Why it's built this way: Comparing all four possible overlap amounts,
and picking whichever is smallest, is a standard, simple technique for
2D rectangle collision that generally produces reasonable-looking
results (landing on top of things, bumping into sides) without needing
much more complex physics — though it can occasionally behave
slightly oddly at sharp corners, which is a known limitation of this
simple approach rather than a bug specific to this code.

Note: an earlier version of this notebook had a cell here containing a
large commented-out (triple-quoted) block defining an older,
alternative way of checking whether the player was standing on the
ground ("is_Grounded"), left in only for reference. That cell has
since been removed from the notebook entirely — there's nothing dead
or inactive left between handle_platform_collision and the Enemy class
below.

--------------------------------------------------------------------
CLASS: Enemy — CELL 16
--------------------------------------------------------------------
What it's for: A simple patrolling hazard that walks back and forth
across a fixed horizontal range and kills the player on contact. This
is new since the last time this notebook was documented — there was no
enemy/hazard system before.

Enemy.__init__(self, x, y, image, moveSpeed=5)
    Sets up one enemy at a given starting position, with a given image
    to draw and a horizontal speed (defaulting to 5 pixels per frame;
    several enemies are given faster custom speeds later — see cell
    20). It also builds an initial "rect" (a rectangle matching its
    position and image size), used for collision checks against the
    player.

Enemy.move(self, minX, maxX)
    Called once per frame for each enemy. It advances the enemy's x
    position by "moveSpeed" (which can be negative, in which case this
    moves it left instead of right) and rebuilds its "rect" to match
    the new position. If the enemy has reached or passed either edge of
    its allowed patrol range ("minX" or "maxX"), its image is flipped
    horizontally (so it visibly turns around) and "moveSpeed" is
    negated — reversing its direction of travel, so it walks back the
    other way. Note that in the main loop (cell 21), every enemy is
    currently given the same range (0 to 2000) regardless of the
    "moveSpeed" argument they were constructed with, so all 11 enemies
    (see cell 20) patrol across the same horizontal span, just at
    different speeds and starting heights.

Enemy.hitPlayer(self, player)
    Called once per frame for each enemy, right after the player's own
    rect has been refreshed via handle_platform_collision (which also
    calls player.get_rect() internally). It refreshes the player's rect
    again itself (via player.get_rect()) to be safe, then checks
    whether the enemy's rect currently overlaps the player's rect; if
    so, it sets "player.dead = True" — this is the other way (besides
    falling off the world, in Player.apply_gravity) the player can die.

--------------------------------------------------------------------
CLASS: CheckPoint — CELL 17
--------------------------------------------------------------------
What it's for: Marks the single win condition of the game — a fixed
point in the world that, once the player reaches it, ends the current
run and sends them back to the start. This is also new since the
notebook was last documented; previously, "winning" was handled
directly inside Camera.render_world by comparing the player's position
against a hardcoded threshold and swapping in a victory background
image — that logic has been replaced by this dedicated class.

CheckPoint.__init__(self, x, y, image, level=1)
    Stores the checkpoint's position, its marker image (the
    exclamation mark, drawn by Camera.render_world), and a "level"
    number that defaults to 1 and — as used in this notebook today —
    is never set to anything else, since there's currently only one
    checkpoint in the world (created in cell 21, at (1600, -10100), the
    same position the old victory-threshold logic used to check
    against). It also builds a "rect" for collision checks.

CheckPoint.win(self, player)
    Refreshes the player's rect (via player.get_rect()) and returns
    True if it currently overlaps the checkpoint's rect, or nothing
    (Python's implicit None, which is "falsy" — treated the same as
    False wherever this is checked) otherwise. This is called once per
    frame from Camera.render_world (see above), which triggers the win
    overlay and resets the player when it returns True.

CELL 18 — Account creation / login (accounts, via shelve)
--------------------------------------------------------------------
What it's for: A small text-based login system that runs once, in the
notebook's own output area (using Python's ordinary "input()"), before
the game window ever opens — the player identifies themselves (and, if
new, picks a permanent character) here, rather than the name/character
being hardcoded in the notebook as they previously were. This is
entirely new; there was no account system documented previously.

How it works: Two small helper functions are defined first,
create_new_account() and log_in(), both of which read and write two
separate shelve save files (see server.py_explained.txt's note on
"shelve" for what that built-in tool is): "users" (mapping a chosen
username to "hash(username)" — not a real password check, just a
placeholder value recorded against that name) and "character_data"
(mapping a username to their chosen character number).

create_new_account() repeatedly asks (via input()) for a username
until one is typed that ISN'T already present as a key in the "users"
shelve file, then records it there, and separately records the
"chosen_character" value (set just before this function is called,
below) into the "character_data" shelve file, keyed by that same
username.

log_in() repeatedly asks for a username until one IS found in the
"users" shelve file, then looks up and returns that username's
previously-chosen character number from the "character_data" shelve
file.

Below those two functions, the cell's own top-level code actually runs
the flow: it asks for the server's IP address (stored as
"server_id" — this replaces the previous version's hardcoded
"127.0.0.1"), then asks whether the player wants to create a new
account or log in ("1" or "2"). If "1", it asks for a desired username
and a character choice (an integer from 1 to 16, matching
pick_character's char_list from cell 2), then calls
create_new_account(). If anything other than "1" (in practice, "2"),
it asks for an existing username and calls log_in() to retrieve that
account's previously-saved character choice.

Note: both branches use the global variable "username" inside the
helper functions (declared with "global username" at the top of each
function) — this is what lets create_new_account() and log_in() update
the same "username" variable that the outer code reads afterward, even
though it's reassigned inside a function.

Why it's built this way: This gives each player a persistent identity
across sessions, independent of and in addition to the position/
character "resume" data the *server* separately remembers by name (see
server.py_explained.txt) — the notebook's local "users"/
"character_data" shelve files exist only on this player's own machine
and track their login/character choice, while the server's "players"
shelve file exists on the server and tracks position/character by
whatever name is sent to it. In practice the two are meant to be kept
in sync (log in with the same name you'd use to resume on the server),
but they're two entirely separate save files with no code enforcing
that connection.

CELL 19 — Connecting to the multiplayer server
--------------------------------------------------------------------
What it's for: Establishes this player's connection to the
multiplayer server before the actual game loop starts, now using the
identity/character chosen in cell 18 rather than hardcoded values.

How it works: Three settings are set from the previous cell's results
— PLAYER_NAME (the username), SERVER_HOST (the server IP address
typed in), and CHARACTER (the character number, either freshly chosen
or loaded back from a previous login).

Then, in case this cell is being re-run after already having
connected once before (for example, while experimenting in Jupyter,
where cells can be re-run out of order or repeatedly), it tries to
close any existing connection first, ignoring the specific error
(NameError) that would occur if no such connection exists yet at all
(the very first time this cell runs — there'd be no "net" variable to
close). It then creates a brand new NetClient(SERVER_HOST, PLAYER_NAME,
CHARACTER) — note the constructor now takes the character number as a
third argument, which gets sent to the server as part of the
JoinRequest (see netcode.py_explained.txt) — which immediately performs
the full join handshake with the server, and prints a confirmation
line showing the assigned player id, chosen character, and resume
position (if any).

--------------------------------------------------------------------
CELL 20 — Enemy instances
--------------------------------------------------------------------
What it's for: Creates the 11 actual Enemy objects (using the Enemy
class from cell 16) that will patrol the world this session, and
collects them into one "Enemies" list for the main loop to use.

How it works: Each enemy is constructed with its own starting (x, y)
position — mostly spaced out vertically to roughly track the rising
path of the islands built earlier — using the shared "enemyImage"
loaded in cell 1, and, for most of them, an explicit "moveSpeed"
argument that generally increases the higher up the enemy is placed
(ranging from the class default of 5 up to 30), making enemies
encountered later in a climb move noticeably faster than the first
one. All 11 are then gathered into a single "Enemies" list, which cell
21's main loop iterates over every frame.

--------------------------------------------------------------------
CELL 21 — The main game loop
--------------------------------------------------------------------
What it's for: This is where the game actually plays — everything
defined in every earlier cell exists to be used here. This single
cell runs continuously, frame after frame, until the player closes
the window.

How it works: Before the loop starts, a Camera is created, and a
Player is created using pick_character(net.char) (cell 2) as its
image — so the player's own on-screen sprite matches the character
number chosen back in cell 18/19, rather than everyone always looking
like the same frog. A CheckPoint is created at (1600, -10100) using the
exclamation-mark image. Background music ("7pm.wav") is loaded and set
to loop forever ("pygame.mixer_music.play(-1)" — a loop count of -1
means "repeat indefinitely"). If the server said this player has a
saved position to resume from (from a previous session), the player's
starting position is overwritten with that saved position instead of
the Player class's default starting spot. A pygame "Clock" object is
also created, which will be used to both measure the frame rate and to
limit how fast the loop runs.

The loop then repeats the following steps every frame, for as long as
"running" stays True:
 1. Checks for any pending window events (like the user clicking the
    window's close button); if a "quit" event is seen, "running" is
    set to False, which will end the loop after this frame finishes.
 2. Reads the keyboard via handle_input (cell 13) to get the current
    left/right/jump state.
 3. Applies that input to the player via Player.move (moving
    left/right and possibly starting a jump).
 4. Moves every enemy in "Enemies" (via Enemy.move, patrolling them
    between x=0 and x=2000) and checks each one against the player
    (via Enemy.hitPlayer) — any enemy currently touching the player
    marks the player dead.
 5. Applies gravity to the player via Player.apply_gravity (pulling
    them downward, slowing/reversing an upward jump, and marking the
    player dead if they've fallen past y=3000).
 6. Resolves collisions against every solid rect in the world via
    handle_platform_collision, which may adjust the player's position
    and stop them from moving through solid ground/platforms, and
    updates player.on_ground from what it returns.
 7. Sends the player's now-final position to the server, and receives
    back the latest known positions of every other connected player,
    via NetClient.update — described fully in netcode.py_explained.txt.
 8. If the player is currently dead (from step 4 or 5): their position
    is reset back to (500, 500), the death-screen overlay is drawn via
    Camera.death_screen, the frame is flipped to actually show it,
    the game is paused for 3 real seconds ("pygame.time.wait(3000)"),
    and "player.dead" is reset to False so normal play resumes on the
    next frame. Otherwise (the ordinary case): the entire scene is
    drawn for this frame via Camera.render_world, passing in the full
    world data (platforms, ground, below tiles, decorations), the
    player, the Enemies list, the CheckPoint, and the list of other
    players just received from the server in step 7. (Camera.render_world
    itself may then trigger the *win* overlay and a position reset, if
    checkPoint.win(player) returns true — see the Camera class,
    above.)
 9. Computes a "status" string, "online" or "OFFLINE" depending on
    "net.connected" — however, unlike an earlier version of this loop,
    this status string is no longer actually used to update the
    window's title bar anywhere in the loop; it's computed but
    currently has no visible effect.
 10. Actually displays everything that was drawn this frame onto the
     screen ("pygame.display.flip()").
 11. Waits just long enough to cap the frame rate at 60 frames per
     second ("clock.tick(60)") — this prevents the game from running
     faster (and therefore differently) on faster computers, and keeps
     it from using more of the computer's processing power than
     necessary.

Once the loop ends (the player closed the window), the connection to
the server is closed via NetClient.close, and pygame itself is shut
down cleanly via "pygame.quit()".

Why it's built this way: This is a completely standard structure for a
real-time game: one big loop that, every single frame, in a fixed
order, handles input, updates game logic (movement, physics, enemies,
collision, networking, death/win checks), then draws the result —
repeated dozens of times per second for as long as the game is
running.
